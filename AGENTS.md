# FlatMark Ticket Management Guidelines

FlatMark is a lightweight, file-based ticketing system designed to be independent of the project's
primary codebase.

## 1. Core Files

- `tickets/`: Directory containing active tickets in individual Markdown files with YAML headers.
- `archive/`: Directory containing completed or obsolete tickets.
- `BOARD.md`: A generated overview of all active tickets. **Do not edit this file manually.**
- `board.py`: A Python script used to synchronize `BOARD.md` with the contents of `tickets/`.
- `VERSION`: File containing the currently installed FlatMark version.

## 2. Usage from Project Root

You can interact with the system without leaving the project root:

- **Create a New Ticket**:
  Automatically find the next ID and create a templated ticket file (which also updates the board):
  ```bash
  python3 flatmark/new.py [T|B|F|S|R|D] "Ticket Title"
  ```
- **Update the Board**:
  ```bash
  python3 flatmark/board.py
  ```
- **Check Version**:
  ```bash
  python3 flatmark/board.py --version
  ```
- **Quick Search**:
  Use your IDE's global search or `grep` to find tickets by ID or keyword across the `tickets/`
  directory.

## 3. Ticket Management Process

### Creating a New Ticket

1. **Determine the Ticket Type**:
   - FlatMark supports alphanumeric sorting. Use the following prefixes for ticket IDs:
      - **`T<number>`**: Tasks (general tasks, chores, and refactoring)
      - **`B<number>`**: Bugs (defects, issues, and regressions)
      - **`F<number>`**: Features (new functionality, user stories)
      - **`S<number>`**: Spikes (research, investigations, prototyping)
      - **`R<number>`**: Releases (deployment checklists, launch prep)
      - **`D<number>`**: Documentation (user guides, READMEs, API docs)
2. **Run the Creation Script**: Run `python3 flatmark/new.py [T|B|F|S|R|D] "Ticket Title"`
   (where `T` is Task, `B` is Bug, `F` is Feature, `S` is Spike, `R` is Release, `D`
   is Documentation).
3. **Edit the Ticket File**: Open the newly created file in `tickets/` (e.g., `tickets/B8.md`) to
   add the description and acceptance criteria.
4. **Add Frontmatter**: Every ticket MUST have a YAML header. You can specify the following optional
   fields to define relations:
   - `parent`: Establishes a parent-child relationship (which nests the ticket visually on the board).
   - `blocked by`: Defines a blocking ticket ID dependency.
   ```markdown
   ---
   id: B8
   priority: P2
   status: Todo
   parent: F2
   blocked by: T1
   ---
   # Ticket Title

   Description goes here.
   ```

### Updating Tickets

1. **Modify the File**: Edit the specific ticket file in `tickets/`.
2. **Update Status/Priority**: Change the values in the YAML frontmatter.

### Archiving Tickets

When a ticket's status is changed to **Done** or **Obsolete**:
1. Update the `status` in the YAML header.
2. Move the file from `tickets/` to `archive/`.

### Synchronizing the Board

After any changes to the `tickets/` directory, run the synchronization script:

```bash
python3 flatmark/board.py
```

## 4. Best Practices for Agents

- **Reference Tickets in Commits**: Use the ticket ID in your commit messages, e.g., `[#T15] Fix bug`.
- **Atomic Changes**: Update the ticket file and run `board.py` in the same PR/commit.
- **Detailed Descriptions**: Include "Acceptance Criteria" or "Implementation Details".
- **Status Progression**: Use `Todo`, `In Progress`, `Done`, or `Obsolete`.
